# 岗位能力映射与项目讲述稿（中文）

> **一句话结论**：这个仓库不是"写了个分析程序"，而是把「行业洞察 → 技术方案 → 可交付系统」这条路走通了，并且明确写清楚哪些事系统**不做**。以下材料可直接用于面试讲述，全部来自仓库里可核验的公开实现。

**适用范围**：云厂商行业解决方案咨询岗（FDE 类），面向零售、农业、文旅酒店、地产、金融服务等客户。本文是**能力映射**，不是履历；不含雇主名、客户名、真实标的、账户、成本、密钥或本机路径。项目仅用于研究与决策支持，不构成投资建议，也不自动执行任何操作。

## 二、四段 STAR 讲述稿（可照念，每段 ≤300 字）

### A｜"数据拉新了，图还是旧的"

- **情境**：周度研究产物由一次取数生成。原本已有"新鲜度检查"，每个源文件也都带了 as-of 日期。
- **任务**：保证发出去的图真的用了最新那次取数。
- **动作**：把流水线从头走一遍，补第二道独立的门——渲染产物的 as-of 必须等于原始取数的 as-of。"取数新、忘了重跑"现在会返回 `render_drift`，直接拦下，并告诉操作者该重跑哪一步。
- **结果**：两类故障都能被看见且能区分；用一条回归测试把这种漂移原样种进去，断言必须被抓住。
- **我会先问客户**：「数据刷新了、但材料没跟着换，通常是谁先发现？」

### B｜"差了近一个数量级的阈值"

- **情境**：某个双值指标沿用两个固定阈值，把读数标成「强」或「弱」。
- **任务**：判断这两个标签到底在描述数据，还是在描述习惯。
- **动作**：拉多年观测序列，算经验分位，再看旧阈值实际落在哪个分位——被当成「强」的那条线其实靠近分布底部，刻度差了近一个数量级。改成由序列推导的五档分位带，阈值进版本化数据文件而不是写在正文里。
- **结果**：标签描述的是"在自己历史里的相对位置"；还留了一个 `legacy_percentile` 函数，以后再有刻度错位，拿证据说话而不是靠感觉。
- **我会先问**：「这个数是谁定的？在你们自己的数据里排第几？」

### C｜"换掉一整章，但决策表一个数不动"

- **情境**：要下线一个分析章节、换上新的背景章节，同时所有下游决策表必须保持原样。
- **任务**：把展示层和数据层拆开。
- **动作**：旧渲染器用一个开关停用（保留不删，方便回滚）；共享证据对象无条件富化；决策表路径零改动；再加一个可选报告日期参数，让同一次运行可复现。
- **结果**：报告换了形状，决策层稳定；用结构锁＋变异测试证明开关真的生效。
- **我会先问**：「这份材料里，哪部分允许改，哪部分绝对不能动？」

### D｜"一句话变成状态机"

- **情境**：业务规则说，风险边界被跌破后，如果"预期有基本面支撑"，可以解除新增暂停。
- **任务**：实现它，但不让模型自己猜"预期"是什么意思。
- **动作**：定义四状态 `NOT_APPLICABLE / FORBID / INSUFFICIENT / ALLOW`。系统**只消费**人工登记、带口径和日期的支撑记录；凡是模型推断的、未核验的、过期的、没有前向复核点的，一律保守降到 `INSUFFICIENT`。`ALLOW` 只解除暂停，加仓仍要推迟到复核点之后。
- **结果**：模糊的"预期"变成可审计的契约；模型能力边界写进了代码，不是写在文档里的一句话。
- **我会先问**：「哪些事实允许模型推断，哪些必须人来登记？」

## 三、高频题与答法要点

| # | 可能被问 | 怎么答（抓手） |
|---|---|---|
| 1 | 为什么要两道门，一个新鲜度检查不够？ | 抓的是两类故障；"源新、产物旧"在只查新鲜度时会以 0 退出码放行。 |
| 2 | 你怎么证明一个阈值是错的？ | 算它在观测序列里的经验分位；标"强"却落在 P15 附近，就该退休，改用分位带。 |
| 3 | 这里大模型的边界在哪？ | 不登记支撑事实、不在两种归因之间裁决、不执行外部动作。 |
| 4 | 数据都对，结论还是错，为什么？ | 先查时点窗口，再查单位/口径，最后查字段契约——消费方到底有没有读过这个字段。 |
| 5 | 怎么设计人工确认门？ | 先分「影响决策」和「只改措辞」；前者要审批、证据、旧版本、测试结果、回滚路径。**卡片被跳过 ≠ 已确认**。 |
| 6 | 为什么要渲染之后再校验断言？ | 模板会漂移：生成时谨慎的措辞，排版后可能变成绝对化、无来源的表述。审计器只读，返回 0/1/2。 |
| 7 | 数据源挂了怎么办？ | 显式标注不可用、降级为观察，禁止备用源冒充主口径。 |
| 8 | 怎么证明你的测试锁不是摆设？ | 变异测试：故意把规则改坏，看测试是否转红；永远不会失败的锁不是锁。 |
| 9 | 客户要求系统自动下结论并执行呢？ | 明确拒绝：仅研究、不接账户、不执行动作、不承诺效果；给决策支持的替代方案。 |
| 10 | 讲一次你推翻自己判断的经历 | 某次驱动归因在双源核验后被改判（两个指标实际同向上行），改判写成规则留痕，而不是悄悄改口。 |

## 五、可复制：60 秒开场白

> "我做的是一个证据优先的周度决策闭环。不让一个模型直接给结论，而是把流程拆成八段、每段单一责任人：收集、验证、合成、仲裁、决策、发布、复盘、进化。真正花功夫的是边界工程——数据契约双门、按分布重定标的阈值、保守降级的后置状态机、渲染后的断言审计。凡是可能影响决策的改动都要过人工确认门，每条规则都用变异测试证明锁得住。它是研究用途：给人准备证据，不碰账户、不执行动作。"

**白板画法（5 个框）**：业务问题→带 as-of 的可观测数据 → 两道硬门 → 证据分层 → 人工门 → 复盘只晋级复现规则。
